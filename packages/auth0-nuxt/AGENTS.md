# AGENTS.md: `@auth0/auth0-nuxt`

Package-level guidance; the [root AGENTS.md](../../AGENTS.md) rules (commits, boundaries, releases) also apply.

This is a **published, security-critical authentication SDK**. Review your own changes with an attacker's mindset.

## Layout

```
src/
  module.ts                     # defineNuxtModule: options, runtime config, handler/plugin/middleware wiring
  types.ts, types/*.d.ts        # public types: RouteConfig, SessionStore, runtime-config & route-rules augmentation
  runtime/                      # code that ships into the user's Nuxt app (not bundled into module.ts)
    composables/use-user.ts           # client+server `useUser()`
    plugins/auth.client.ts            # hydrates useUser() from the profile route (unless hydrateUser: false)
    middleware/auth.server.ts         # global route middleware `auth0`
    server/api/auth/*.ts              # login, callback, logout, backchannel-logout, profile handlers
    server/composables/use-auth0.ts   # `useAuth0(event)`: server-only auth client (login, logout, passkeys, tokens)
    server/plugins/auth.server.ts     # Nitro plugin: resolves the SSR user (route rules are set in module.ts)
    server/utils/                     # cookie-handler, url (toSafeRedirect), resolve-ssr-user, default session store
test/                           # Nuxt e2e tests (*.test.ts) + fixtures/ (small Nuxt apps built per test)
dist/                           # build output of `nuxt-module-build`; generated, never edit
```

A new runtime file only takes effect once `src/module.ts` registers it (`addServerHandler`, `addPlugin`,
`addImportsDir`, …); runtime paths are resolved through `createResolver`, so keep them relative to `module.ts`.

## Commands

```bash
npm run build -w @auth0/auth0-nuxt       # nuxt-module-build (prebuild runs `nuxt-module-build prepare`)
npm run lint -w @auth0/auth0-nuxt
npm run typecheck -w @auth0/auth0-nuxt   # tsc --noEmit; requires a prior build, see below
npm run test:unit -w @auth0/auth0-nuxt   # vitest run ./src/**
npm run test:e2e -w @auth0/auth0-nuxt    # vitest run ./test/**  (slow; builds Nuxt fixtures)
npm run test:ci -w @auth0/auth0-nuxt     # what CI runs: with coverage
```

- `typecheck` needs `.nuxt/` types and a built `dist/` (the passkeys example imports the package through `dist/`). Run
  `npm run build -w @auth0/auth0-nuxt` first, or use the root `npm run typecheck`, which does it for you.
- `build:watch` was removed because it referenced a nonexistent `src/index.ts`. Rebuild with `build` instead.

## Testing

- **Unit**: `src/**/*.spec.ts`, co-located with the code they test. Use these for logic (utils, handlers,
  composables); they need no network and no credentials.
- **E2E**: `test/*.test.ts` using `@nuxt/test-utils` `setup()` against the apps in `test/fixtures/*`. Playwright
  browsers are required (`npx playwright install`, already run by `pretest`).
- `test/rendering.test.ts` talks to a **real Auth0 tenant** and needs `NUXT_AUTH0_DOMAIN`, `NUXT_AUTH0_CLIENT_ID`,
  `NUXT_AUTH0_CLIENT_SECRET`, `NUXT_AUTH0_TEST_USERNAME` and `NUXT_AUTH0_TEST_PASSWORD` (CI provides them as
  secrets). Without them it fails, which is expected locally. Do not "fix" it by mocking or editing it; run the
  other files instead (`npx vitest run test/<file>`).
- Passkey e2e tests use fakes under `test/fixtures/passkeys/fakes/` and also build `examples/example-nuxt-passkeys`
  (`test/global-setup.ts` prepares its `.nuxt/tsconfig.json`), so changes to that example can break package tests.
- `packages/auth0-nuxt/.nuxtrc` is generated by Nuxt when tests load it (it records `@nuxt/test-utils`' module
  version under `setups`). It is gitignored; do not edit or commit it.
- Cover failure and attack paths (missing, expired or tampered tokens; invalid state; open-redirect attempts), not only
  the happy path. Prefer asserting behavior over implementation details.

## Security invariants

Do not weaken these; ask first if a change appears to require it.

- **Secrets stay private.** Session secret, client secret and tokens live in private `runtimeConfig.auth0`, never in
  `runtimeConfig.public` (which is sent to the browser). Never log them or put them in errors or responses.
- **Redirects are validated.** Every `returnTo` / redirect target goes through `toSafeRedirect`
  (`runtime/server/utils/url.ts`) and must be same-origin with the app base URL.
- **Fail closed.** Auth middleware and handlers deny by default and allow only on an explicit positive check.
- **Cookies**: session and transaction cookies are written by the `@auth0/auth0-server-js` stores through
  `NuxtCookieHandler` (`runtime/server/utils/cookie-handler.ts`), which passes options straight to h3. Never override
  or drop their security attributes (`httpOnly`, `secure`, `sameSite`); `maxAge` is in **seconds**.
- **Backchannel logout** validates the logout token before destroying any session.
- **State, nonce and PKCE** are generated, persisted and validated across login and callback; never skip or reuse them.
- **`/auth/profile`** must never be cached: `module.ts` forces `cache: false` on that route rule because Nitro's cache
  ignores cookies and would leak one user's claims to another. Keep that intact.
- **Server-only code** (`runtime/server/**`, `useAuth0`) must not end up in the client bundle or expose token material
  to client-side state.

## Public API

Anything exported from `src/module.ts` / `src/types.ts`, the shape of `ModuleOptions`, the default routes
(`/auth/login`, `/auth/callback`, `/auth/logout`, `/auth/backchannel-logout`, `/auth/profile`), runtime config keys
and the `useUser()` / `useAuth0()` surfaces are public API.

- Treat any change to them as potentially breaking, and ask before making one.
- Keep exported symbols explicitly typed with accurate JSDoc (TypeDoc generates `docs/` from `src/module.ts`).
- Avoid `any`, unchecked `as` casts and non-null assertions (`!`) in `src/`; prefer `unknown` plus narrowing.
- Await or explicitly handle every promise in handlers and middleware.

## Docs

Behavior changes must update `README.md` (setup and configuration) and `EXAMPLES.md` (recipes) in this package. Do not
